How Scratchpad
was built.

A compact desktop editor grew from one idea: writing should survive without asking the writer to think about files. This report traces the C structures, GTK event flow, persistence layer, and iterations behind that idea.

C11 GTK 4.12+ GLib / GIO 844 lines of authored C 0 database dependencies 8–32 pt adjustable type
01 · The brief

Two promises shaped the code.

The implementation stayed deliberately local and small. Every later feature had to preserve these two properties.

01

Writing is continuously durable

Each tab owns a private draft. Edits schedule a short delayed write, so the working text survives application restarts without a conventional save workflow.

02

Tabs are independent notes

Every tab carries its own identity, text buffer, timer, title, draft path, and optional export path. Adding a tab means adding one complete unit of state.

ScratchpadTab

The tab struct is the core unit: stable UUID, label, widgets, text buffer, draft location, optional export location, and the active auto-save timer. 

typedef struct {
  char *id;
  char *draft_path;
  char *export_path;
  GtkTextBuffer *buffer;
  guint autosave_source;
} ScratchpadTab;

The app struct supplies the context shared by all tabs: the GTK application and window, notebook, status surface, ordered pointer array, session paths, and shared editor typography.

03 · Auto-save

The hot path is four small steps.

A debounce keeps typing responsive and collapses a burst of keystrokes into one disk write.

GTK emits changed

Each tab’s GtkTextBuffer is connected to a buffer-change callback.

The old timer is cancelled

If another keystroke arrives within the delay, its pending write is removed.

A 450 ms timer is scheduled

The UI immediately reports “Saving…” while GLib’s main loop holds the work.

The complete buffer is written

Text is read between the buffer bounds and persisted with g_file_set_contents. 

static void buffer_changed_cb(
    GtkTextBuffer *buffer,
    gpointer user_data) {
  ScratchpadTab *tab = user_data;

  if (tab->autosave_source != 0)
    g_source_remove(tab->autosave_source);

  set_status(tab->app, "Saving…");
  tab->autosave_source = g_timeout_add(
      450, autosave_cb, tab);
}
Why debounce?

Writing on every character is unnecessary churn; waiting until typing pauses keeps the model simple without making durability feel delayed.

04 · Persistence

Plain files instead of a database.

Content and metadata have different jobs, so they are stored separately.

$XDG_DATA_HOME/
└── scratchpad/ # mode 0700
   ├── session.ini
   └── tabs/
      ├── 4b2… # UTF-8 text
      ├── 906…
      └── c11…

Draft files hold only text

UUID-based names make titles safe to change and prevent two similarly named notes from colliding.

One key file describes the session

GKeyFile records ordered tab IDs, display titles, optional export paths, the active tab index, and the preferred editor text size.

Restore rebuilds normal tabs

Startup reads the key file, loads each draft, then calls the same new_tab path used by a fresh note. There is no separate “restored tab” implementation.

05 · Development path

The app improved in layers.

Each iteration addressed a concrete behavior while preserving the small single-process design.

Phase 01

Foundation

A GTK application window, notebook, text views, header controls, Makefile, and desktop entry established the product shell.

Phase 02

Durability

Per-tab UUID drafts, a 450 ms debounce, session metadata, restoration, and shutdown flushing formed the persistence layer.

Phase 03

Export & removal

Manual file export was kept separate from drafts. Tab removal gained an explicit destructive confirmation.

Phase 04

Tooling

pkg-config supplies GTK flags; a compilation database aligns Clangd and the real compiler.

Phase 05

Modern GTK

Deprecated chooser and message APIs were replaced by asynchronous GtkFileDialog and GtkAlertDialog.

Phase 06

Native polish

Hardcoded light colors were removed for system-theme inheritance, then wraparound keyboard tab navigation was added.

Phase 07

Windows release

A GUI-subsystem build, executable resources, DPI manifest, portable GTK bundle, embedded editor font, licenses, and CI artifact workflow completed the cross-platform release path.

Phase 08

Crisp shell icons

Size-specific 16–256 pixel artwork now feeds both GTK resources and the Windows ICO, avoiding runtime downscaling in taskbars and window switchers.

Phase 09

Adjustable text

Ctrl+wheel, Ctrl++, Ctrl+-, and Ctrl+0 update a shared CSS provider from 8–32 pt. The selected size is restored on launch.

06 · Engineering decisions

Small choices carry the product.

The implementation favors directness, recoverability, and GTK-native behavior over abstraction.

Files over SQLite

Inspectability wins

Drafts remain ordinary UTF-8 data. No schema, migration, query layer, or database recovery path is needed.

IDs over pointers

Async callbacks stay safe

Dialog requests store a tab ID, then look the tab up when the callback fires. A tab may disappear while a dialog is open without leaving a stale tab pointer.

GTK actions

One command, many entry points

Header buttons, menu items, and keyboard accelerators all target the same GSimpleAction callbacks.

Theme inheritance

Native contrast by default

A small dynamic CSS provider controls spacing, font family, and the current editor size. GTK remains responsible for surfaces, text, selection, and symbolic icon colors.

Explicit ownership

C memory stays legible

Tab cleanup removes timers and frees owned strings, while g_autofree and g_autoptr handle short-lived values and GObjects.

Modulo navigation

Tab switching wraps

The next index is (current + offset + count) % count, supporting forward and backward movement with one helper.
